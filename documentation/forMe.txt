Step 5.1 — Understand HTTP request structure
There are three ways to pass information to an API.

1. Route parameters (req.params)
GET /api/users/12345

Access:
req.params.id
Used to identify a specific resource.

2. Query parameters (req.query)
GET /api/users?page=2&limit=10

Access:
req.query.page
req.query.limit
Used for filtering, sorting, searching and pagination.

3. Request body (req.body)
PATCH /api/users/12345
{
    "name": "Prabhat Kumar",
    "email": "new@example.com"
}

Access:
req.body.name
req.body.email
Used to send data for creating or modifying resources.


Step 5.2 — HTTP status codes
These are important for both backend development and technical interviews.

Code	                        Meaning	Example
200	    OK	                    Successful GET/PATCH
201	    Created	User            created
204	    No Content	            Successful deletion without response body
400	    Bad Request	            Invalid input
401 	Unauthorized	        Missing/invalid authentication
403	    Forbidden	            Insufficient permissions
404	    Not Found	            User doesn't exist
409	    Conflict	            Duplicate email
422	    Unprocessable Entity	Semantically invalid input
429	    Too Many Requests	    Rate limit exceeded
500	    Internal Server Error	Unexpected server failure

Important distinction:
- 401: Who are you? Authentication is missing or invalid.
- 403: I know who you are, but you aren't allowed to do this.
We'll use these distinctions when implementing authentication and role-based authorization.




Step 5.2: Request Validation with Zod

Understand the important Zod methods:
Method	            Purpose
string()	        Value must be a string
trim()	            Removes leading/trailing spaces
min(2)	            Minimum length is 2
max(80)         	Maximum length is 80
email()	            Validates email format
optional()	        Field is not mandatory
default(10)	        Uses 10 if the value is missing
coerce.number()	    Converts query strings into numbers
strict()	        Rejects unexpected fields
refine()	        Adds custom validation logic

Important: .strict() is useful for security. For example, a user must not be able to set their own role: "ADMIN" or credits: 999999 through the profile update endpoint.



7. What have we achieved?
Before Zod:
- Controllers had to manually check incoming data.
- Invalid values could reach your service layer.
- Different endpoints could implement inconsistent validation.
After Zod:
- Validation rules are centralized.
- Middleware is reusable across routes.
- Invalid requests are rejected before reaching controllers.
- Unexpected fields are rejected.
- Pagination values are converted and validated automatically.
One architectural distinction: Zod validates request data; Mongoose validates data at the database/model layer. We need both because not every database operation necessarily passes through these HTTP routes.





Step 5.3: Standardized API Responses
Right now, different controllers may return slightly different JSON formats. That becomes difficult to maintain as the application grows.

For example, we want successful responses to follow one predictable structure:
{
  "success": true,
  "message": "User created successfully",
  "data": {
    "id": "123",
    "name": "Prabhat"
  }
}


And errors to follow another:
{
  "success": false,
  "message": "User not found",
  "errors": []
}
This is an API response contract: frontend code can rely on a predictable structure regardless of which endpoint it calls.

2. Use the utility in your controllers
